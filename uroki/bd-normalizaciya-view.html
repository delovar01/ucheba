Шаг 2 из 9

Нормализация и нулевая нормальная форма

Определения с лекции 1. Нормализация это проверка логической ER-модели по правилам, чтобы понять, качественно ли она составлена. Нормальная форма это набор таких правил. Форм девять, на курсе первые три, и перед ними ещё нулевая.

0НФ, ненормализованная форма: в клетке может лежать несколько значений сразу, списком. Так обычно выглядят данные из Excel или из головы.

Те же запуски в 0НФ, одна строка на человека:

Повторов людей нет, зато каждый запрос превращается в мучение. Чтобы найти, кто работал с Titanic, придётся искать кусок внутри текста. Посчитать запуски через COUNT вообще не выйдет: строк две, а запусков пять.

Нормализация: проверка модели по правилам. Нормальная форма: набор правил, на курсе 0НФ–3НФ.

Шаг 4 из 9

Зависимость: что от чего зависит

Для 2НФ и 3НФ нужно одно слово. Если знаешь набор данных, ты знаешь и число строк в нём: iris значит 150, где бы iris ни встретился. А по числу строк исследователя не узнать.

Функциональная зависимость A → B: по значению A однозначно определяется значение B. Читается «B зависит от A». В одинаковых A всегда одинаковое B.

Зависимости широкой таблицы:

  • researcher → grp: группа зависит только от человека
  • dataset → rows: число строк зависит только от набора
  • model → framework: библиотека зависит только от модели
  • (researcher, dataset, model) → status: статус зависит от всей тройки
Сделай сам. Верна ли зависимость, проверь по таблице: а) framework → model, б) dataset → status, в) (researcher, dataset) → status?
Показать ответСкрыть ответ

Проверить зависимость по пяти строкам примера и объявить её верной. Зависимость это правило про любые данные, а не совпадение в маленькой выборке. Спрашивай себя: может ли в жизни быть иначе?

A → B: по A однозначно знаем B. Проверяем по смыслу, а не по нескольким строкам.

В нормализованной базе каждый факт хранится в одном месте. Группа человека лежит в одной строке, число строк набора в одной строке. Связи держатся на ключах, и данные снова собирают через JOIN.

Шаг 8 из 9

CREATE VIEW: сохранить запрос как таблицу

Обратная сторона нормализации: чтобы увидеть запуски с именами, каждый раз пишешь три JOIN. Это можно сделать один раз.

CREATE VIEW runs_full AS
SELECT r.full_name, d.name AS dataset, m.name AS model, e.status
FROM experiments e
JOIN researchers r ON r.id = e.researcher_id
JOIN datasets d    ON d.id = e.dataset_id
JOIN models m      ON m.id = e.model_id;

Дальше с runs_full работают как с таблицей:

SELECT * FROM runs_full WHERE status <> 'done';
full_namedatasetmodelstatus
Щайхутдинов АзатTitanicRandomForestfailed
Щайхутдинов АзатMNISTResnetrunning

Представление, по-английски view, по слайду 26 лекции 29.09: запрос, который хранится в базе. Оно выглядит и действует как таблица, но своих данных у него нет. Когда ты пишешь SELECT … FROM runs_full, база подставляет сохранённый запрос и выполняет их вместе.

<> значит «не равно». На лекции такие таблицы назвали виртуальными, рядом с постоянными из CREATE TABLE, производными из подзапроса и временными, которые живут до конца сеанса.

Запустить CREATE VIEW runs_full второй раз, поправив запрос. PostgreSQL ответит relation "runs_full" already exists. Для замены пишут CREATE OR REPLACE VIEW runs_full AS …, а убрать совсем можно через DROP VIEW runs_full;.

CREATE VIEW имя AS SELECT …: сохранённый запрос, работает как таблица, своих данных нет.

Поправить: CREATE OR REPLACE VIEW. Убрать: DROP VIEW.

Шаг 9 из 9

Представление всегда свежее

Раз своих данных у представления нет, оно каждый раз показывает то, что сейчас лежит в таблицах. Проверим на пробе, которую потом откатим, как в уроке про UPDATE:

BEGIN;
UPDATE experiments SET status = 'done' WHERE id = 8;
SELECT * FROM runs_full WHERE status <> 'done';
ROLLBACK;

Внутри пробы останется одна строка, Titanic failed. Запуск 8 на MNIST стал done, и представление сразу это увидело, хотя его никто не пересоздавал. После ROLLBACK всё вернётся как было.

Представление не копия данных. Меняешь таблицы, меняется и то, что показывает представление. Поэтому его используют, чтобы не писать один и тот же длинный JOIN и чтобы показать человеку только нужные столбцы, без почты и прочего лишнего.
