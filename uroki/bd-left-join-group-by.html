LEFT JOIN и GROUP BY

Базы данных · под самостоятельную 2, задания 8–11 · около 50 минут

Ты уже умеешь доставать строки через SELECT, фильтровать через WHERE, сортировать через ORDER BY и склеивать две таблицы через JOIN. Сегодня две новые вещи: как не потерять строки при склейке и как считать по группам. Девять шагов, в каждом одна новая мелочь.

Как проходить: читаешь шаг, решаешь «сделай сам» сам и только потом открываешь ответ. В рамке «Главное из шага» суть шага в двух строках, к ней возвращайся перед самостоятельной. Если в шаге что-то непонятно, дальше не иди: сначала задай вопрос по этому шагу.

Большие и маленькие буквы в командах SQL не важны: SELECT и select значат одно и то же. В уроке команды большими, чтобы их было видно в тексте. Ты пишешь маленькими, это правильно.

Шаг 1 из 9

Обычный JOIN теряет тех, у кого нет пары

Начнём с того, что ты уже знаешь. Склеим студентов с их заказами:

SELECT s.name, o.item
FROM students s
JOIN orders o
  ON o.student_id = s.id;

s и o это короткие имена таблиц. Их пишут сразу после названия таблицы, чтобы дальше писать s.name вместо students.name. После ON стоит правило склейки: строку заказа приклеиваем к студенту, если номер студента в заказе равен его id.

JOIN оставляет только строки, для которых нашлась пара. Студент без заказов в результат не попадёт.

Шаг 2 из 9

LEFT JOIN сохраняет всех из левой таблицы

Часто терять нельзя: нужен список всех студентов, даже тех, кто ничего не заказал. Для этого меняем одно слово:

SELECT s.name, o.item
FROM students s
LEFT JOIN orders o
  ON o.student_id = s.id;

Откуда «левая» и «правая». Запиши середину запроса в одну строку: students LEFT JOIN orders. Слева от слова JOIN стоит students, это левая таблица. Справа orders, это правая. То есть левая стоит после FROM, правая после JOIN.

Ещё понадобится слово NULL. Оно значит «значения нет»: это не ноль и не пустая строка, это пустота в клетке.

LEFT JOIN оставляет все строки левой таблицы. Если пары нет, в столбцах правой таблицы ставится NULL.

Левая таблица стоит после FROM, правая после JOIN.

Шаг 4 из 9

Найти тех, у кого нет пары

Это задание 10 из самостоятельной: «записи без пары». Берём результат шага 2 и оставляем только строки, где заказа не нашлось:

SELECT s.name
FROM students s
LEFT JOIN orders o

В результате одна строка: Гоша.

IS NULL проверяет, что значения нет. Писать = NULL нельзя: NULL ничему не равен, даже другому NULL, поэтому такое сравнение не проходит ни для одной строки.

Проверяем o.id, потому что у настоящего заказа id заполнен всегда. Если он пустой, значит заказа нет вообще.

Кто без пары: LEFT JOIN + WHERE <id правой таблицы> IS NULL.

Шаг 5 из 9

Агрегатная функция: много строк → одно число

Теперь вторая тема, подсчёты. Пока без склеек, только таблица orders:

SELECT COUNT(*) FROM orders;   -- 5
SELECT SUM(price) FROM orders; -- 480

Серый текст после -- это комментарий. База его не читает, это пометка для человека. Здесь в комментарии записан ответ.

Агрегатная функция берёт много строк и отдаёт одно число. COUNT(*) считает строки, SUM складывает, AVG считает среднее, MIN и MAX находят наименьшее и наибольшее.

Проверь глазами: заказов пять, 120 + 60 + 120 + 90 + 90 = 480.

Сделай сам. Напиши запрос, который выдаст цену самого дорогого заказа и среднюю цену заказа, оба числа в одной строке. Посчитай ответ руками.
Показать ответСкрыть ответ 
SELECT MAX(price), AVG(price)
FROM orders;

120 и 96, потому что 480 / 5 = 96. Две функции через запятую дают одну строку с двумя столбцами. В DBeaver среднее покажется как 96.0000000000000000: это то же число 96, просто база пишет дробную часть.

Добавить к функции обычный столбец: SELECT item, COUNT(*) FROM orders; PostgreSQL ответит ошибкой column "orders.item" must appear in the GROUP BY clause. COUNT сворачивает пять строк в одну, а товар в каждой строке свой. Какой из них поставить рядом с числом, база не знает. Это чинит следующий шаг.

COUNT(*) считает строки. SUM, AVG, MIN, MAX считают по столбцу. Без группировки итог всегда одна строка.

Шаг 6 из 9

GROUP BY: раскладываем строки по кучкам

Хотим знать не «сколько заказов всего», а «сколько у каждого студента». Для этого строки сначала раскладывают по кучкам:

SELECT student_id, COUNT(*)
FROM orders
GROUP BY student_id;

GROUP BY student_id собирает в одну кучку строки с одинаковым student_id. Агрегатная функция считается внутри каждой кучки отдельно, и на каждую кучку выходит одна строка результата.

В DBeaver кучки могут прийти в другом порядке, например 3, 2, 1. Без ORDER BY база порядок не обещает, так же будет и в шагах 7 и 8. Нужен порядок, допиши в конце ORDER BY student_id.

GROUP BY x: одна кучка на каждое значение x, одна строка результата на кучку.

В SELECT можно только то, что стоит в GROUP BY, и агрегатные функции.

Шаг 7 из 9

Кучки по имени: GROUP BY после JOIN

Номера студентов читать неудобно, хочется имена. Имена лежат в другой таблице, поэтому сначала склеиваем, потом раскладываем по кучкам:

SELECT s.name, COUNT(*)
FROM students s
JOIN orders o
  ON o.student_id = s.id
GROUP BY s.name;

Группировать можно по столбцу любой из склеенных таблиц. База работает по порядку: FROM и JOIN собирают большую таблицу, GROUP BY режет её на кучки, SELECT считает в каждой.

Шаг 9 из 9

HAVING: фильтр по кучкам

Это задание 11 из самостоятельной. Нужны только те студенты, у кого два заказа и больше:

SELECT s.name, COUNT(o.id)
FROM students s
LEFT JOIN orders o
  ON o.student_id = s.id
GROUP BY s.name
HAVING COUNT(o.id) >= 2;

В результате одна строка: Аня, 3.

HAVING отбирает кучки по их итогу. Он работает после GROUP BY, когда числа уже посчитаны. WHERE работает раньше, со строками, и итогов кучек ещё не знает.

Сделай сам. Напиши запрос: студенты, которые потратили больше 100 рублей, и сколько именно. Сначала посчитай руками, кто пройдёт.
Показать ответСкрыть ответ 
SELECT s.name, SUM(o.price)
FROM students s
JOIN orders o
  ON o.student_id = s.id
GROUP BY s.name
HAVING SUM(o.price) > 100;

Аня 270 и Борис 120. Вика с 90 не прошла. Тут хватит обычного JOIN: кто ничего не заказывал, больше 100 всё равно не потратил.

Написать условие на сумму в WHERE: WHERE SUM(o.price) > 100. PostgreSQL ответит aggregate functions are not allowed in WHERE. Условие на обычный столбец пишут в WHERE, на итог кучки в HAVING.

Порядок записи запроса целиком:

SELECT … FROM … JOIN … ON … WHERE … GROUP BY … HAVING … ORDER BY … LIMIT …

WHERE работает до кучек, со строками. HAVING после, с итогами.

Почему 16.10 JOIN и LEFT JOIN выдали одно и то же

16.10 в твоей базе у каждого исследователя были запуски (строки в experiments). Гоши там не было, терять некого, и оба запроса дали одинаковый ответ. Это шаг 3: когда у всех есть пара, LEFT JOIN ничем не отличается от JOIN.

С 20.10 свой Гоша в базе уже есть: Смирнов Олег, у него ни одного запуска. Запусти запрос из шага 8 на researchers и experiments, и он покажет Олега с нулём, а обычный JOIN его потеряет. Если Олега в базе нет, добавь человека без запусков сам, одной строкой:

  (full_name, email, grp)
VALUES

   'petrov@example.com',
   'РИ-250932');

INSERT INTO добавляет в таблицу одну строку. В скобках после имени таблицы стоят столбцы, которые заполняем. После VALUES идут их значения в том же порядке. email в твоей таблице не может повторяться у двух людей, поэтому даём выдуманный, которого в базе точно нет. Если база ругнётся на какой-то другой столбец, посмотри, какие столбцы есть: SELECT * FROM researchers;

5. В своей базе ml_tracker найди исследователей, у которых нет ни одного запуска. Запусти в DBeaver, впиши запрос и кого он выдал. Если результат пустой, напиши, почему так может быть.
