Шаг 1 из 9

CASE ставит строке метку

Хотим рядом с каждым запуском написать словами, хороший он или нет. Хорошим считаем accuracy от 0.8.

SELECT id, accuracy,
  CASE
    WHEN accuracy >= 0.8 THEN 'хорошо'
    ELSE 'слабо'
  END AS ocenka
FROM runs;

Читается как обычная фраза: «в случае (CASE), когда (WHEN) точность от 0.8, тогда (THEN) пиши „хорошо“, иначе (ELSE) пиши „слабо“, конец (END)». AS ocenka — имя нового столбца, ты так уже называл столбцы с COUNT.

CASE — это новый столбец, который считается для каждой строки отдельно по условию. Строки он не отбрасывает, в отличие от WHERE.

Шаг 2 из 9

Несколько веток: порядок решает

Меток может быть больше двух. Это задание 12 из самостоятельной.

SELECT id, accuracy,
  CASE
    WHEN accuracy >= 0.9 THEN 'отлично'
    WHEN accuracy >= 0.8 THEN 'хорошо'
    WHEN accuracy >= 0.7 THEN 'средне'
    ELSE 'слабо'
  END AS ocenka
FROM runs;

База проверяет ветки WHEN сверху вниз и берёт первую, где условие выполнилось. Остальные ветки для этой строки уже не смотрит.

Возьмём 0.91. Первая ветка: 0.91 ≥ 0.9, да. Метка «отлично», дальше не проверяем, хотя 0.91 ≥ 0.8 тоже верно.

Сделай сам. Переставь ветки в обратном порядке: сначала >= 0.7, потом >= 0.8, потом >= 0.9. Какие метки получат запуски 1, 3 и 4?

Все три получат «средне». 0.91, 0.78 и 0.85 — каждое ≥ 0.7, первая же ветка срабатывает, до «хорошо» и «отлично» база не доходит. Метки «отлично» не будет ни у кого.

Думать, что база выберет «самую подходящую» ветку. Она берёт первую подходящую. Поэтому ветки пишут от самой строгой к самой мягкой.

Ветки проверяются сверху вниз, срабатывает первая подходящая. Пиши от строгого условия к мягкому: 0.9 → 0.8 → 0.7.

Шаг 3 из 9

NULL и CASE без ELSE

Вернёмся к шагу 1. У запуска 2 точности нет. Условие NULL >= 0.8 база не может назвать ни верным, ни неверным, она считает его «неизвестно». Ветка срабатывает только на «верно», поэтому дошло до ELSE.

Теперь уберём ELSE совсем:

SELECT id, status,
  CASE
    WHEN status = 'done'   THEN 'готово'
    WHEN status = 'failed' THEN 'упал'
  END AS po_russki
FROM runs;

Если ни одна ветка не подошла, а ELSE нет, CASE выдаёт NULL.

Шаг 4 из 9

Посчитать «особые» строки в кучке

Это задание 13. Для каждого исследователя нужно два числа: сколько всего запусков и сколько из них закончились (done).

SELECT researcher,
  COUNT(*) AS vsego,
  SUM(CASE WHEN status = 'done' THEN 1 ELSE 0 END) AS gotovo
FROM runs
GROUP BY researcher;

CASE превращает каждую строку в 1 (подходит) или 0 (не подходит). SUM складывает эти единицы и нули по кучке. Сумма единиц и есть количество подходящих строк.

Кучка Ани: запуски 1, 2, 6. Статусы done, failed, running → 1, 0, 0 → сумма 1.

researchervsegogotovo

Вика11

Показать ответСкрыть ответ 
SELECT researcher,
  SUM(CASE WHEN accuracy >= 0.8 THEN 1 ELSE 0 END) AS horoshih
FROM runs
GROUP BY researcher;

Аня 1 (только 0.91), Борис 0 (0.78 и 0.62), Вика 1 (0.85). Пустые точности Ани дают 0: условие с NULL не срабатывает, идёт ELSE 0.

Написать COUNT(CASE … THEN 1 ELSE 0 END). COUNT считает все непустые значения, а 0 тоже непустой. Получится просто число запусков: Аня 3, Борис 2, Вика 1. С COUNT работает только вариант без ELSE, но проще запомнить связку SUM + 1 и 0.

Сколько особых в кучке:

SUM(CASE WHEN условие THEN 1 ELSE 0 END)

С SUM, не с COUNT.

EXTRACT достаёт из даты кусок

Переходим к датам. Иногда нужна не вся дата, а только месяц.

SELECT id, started_at,

EXTRACT(часть FROM дата) вынимает из даты одно число. Часть пишется по-английски: YEAR — год, MONTH — месяц, DAY — день месяца.

Запуски 1 и 2 сентябрьские, получат 9. Остальные октябрьские, получат 10.

SELECT id, EXTRACT(DAY FROM started_at) AS den
FROM runs;

У запуска 3 дата 2026-10-03, будет 3. Всего: 14, 28, 3, 5, 12, 14.

Перепутать месяц и день, потому что в жизни мы пишем «3.10». В базе дата всегда год-месяц-день, поэтому 2026-10-03 — 3 октября, а не 10 марта.

Шаг 7 из 9

День недели

На лабе 14.10 спрашивали про EXTRACT(isodow FROM …). Это номер дня недели.

SELECT EXTRACT(ISODOW FROM DATE '2026-10-14');  -- 3
SELECT EXTRACT(ISODOW FROM DATE '2026-10-18');  -- 7
SELECT EXTRACT(DOW    FROM DATE '2026-10-18');  -- 0

DATE '2026-10-14' — так пишут дату прямо в запросе, без таблицы. 14 октября 2026 — среда, 18-е — воскресенье.

ISODOW считает по-нашему: понедельник 1, воскресенье 7. DOW считает по-американски: воскресенье 0, понедельник 1, суббота 6. Отличаются только у воскресенья.

Сделай сам. Сколько запусков в нашей таблице сделано в выходные? Напиши запрос с ISODOW и проверь ответ по календарю: 3 октября 2026 — суббота.
Показать ответСкрыть ответ 
SELECT COUNT(*)
FROM runs
WHERE EXTRACT(ISODOW FROM started_at) IN (6, 7);

Один, запуск 3 (суббота). Остальные: 14.09, 28.09, 5.10, 12.10 — понедельники, 14.10 — среда.

Взять DOW и написать IN (6, 7). В DOW воскресенье — 0, а 7 не бывает вообще, воскресные запуски потеряются. С DOW выходные — это IN (0, 6).

ISODOW: пн 1 … вс 7. DOW: вс 0, пн 1 … сб 6.

Выходные: ISODOW IN (6, 7).

Шаг 8 из 9

TO_CHAR: дата в привычном виде

Тоже с лабы 14.10. Дата 2026-10-03 читается неудобно. Хочется 03.10.2026.

SELECT id, TO_CHAR(started_at, 'DD.MM.YYYY') AS data
FROM runs;

TO_CHAR(дата, 'шаблон') превращает дату в текст по шаблону. В шаблоне DD — день двумя цифрами, MM — месяц двумя цифрами, YYYY — год четырьмя. Точки и всё остальное копируются как есть.

Результат: 14.09.2026, 28.09.2026, 03.10.2026, 05.10.2026, 12.10.2026, 14.10.2026.

Сделай сам. Какой шаблон даст для запуска 3 текст 2026/10?
Показать ответСкрыть ответ

TO_CHAR(started_at, 'YYYY/MM'). Сначала год, потом косая черта как есть, потом месяц.

Написать MI вместо MM, потому что «минуты» и «месяц» оба на М. MI — минуты, у даты без времени выйдет 2026/00. Месяц — только MM. В MySQL этой функции нет, там DATE_FORMAT(дата, '%Y/%m').

TO_CHAR(дата, 'DD.MM.YYYY') → текст 03.10.2026.

Результат — текст, а не дата: считать по нему нельзя, только показывать.

Как это ложится на самостоятельную 2

В твоей базе ml_tracker есть всё нужное: у experiments столбцы status и created_at (дата запуска), у researchers тоже есть created_at. Столбца started_at в твоей базе нет, он только в учебной таблице runs.

  • Задание 13, особые в кучке — шаг 4. На твоей базе это кучки по researcher_id в таблице experiments.
  • Задание 15, аналитика по датам — шаги 5–7.
  • created_at у тебя TIMESTAMP, то есть дата со временем. EXTRACT и TO_CHAR работают с ним точно так же.
  • Задания 14, 16 — тот же GROUP BY, что в прошлом уроке. Задание 17 — оконные функции, к нему следующий урок.
