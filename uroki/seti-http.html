Протокол HTTP

Сети · лекция 3, пт 25.09, «Прикладной уровень. Протокол HTTP» · на зачёт и к лабам с Postman · около 60 минут

HTTP это протокол прикладного уровня, по которому браузер, бот или Postman, программа для ручной отправки запросов из шага 11, просит у сервера ресурс и получает ответ. Тема лекции подтверждена записью, но слайдов и текста лекции нет, поэтому урок по учебнику Куроуза и Росса, глава 2. Одиннадцать шагов: запрос и ответ, адрес URL, устройство запроса, методы, ответ, коды состояния, свойства методов, cookie, соединения, HTTPS и инструменты лабы.

Все запросы урока настоящие, их можно повторить командой curl. Это программа, которая отправляет HTTP-запрос из командной строки и печатает ответ. Она есть в Windows 10 и 11. Ключом называют добавку к команде через минус, например -I, она меняет поведение команды. Запускай в «Командной строке», cmd. В PowerShell слово curl занято другой командой, там пиши curl.exe. Нужны уроки основы сетей и адреса и TCP.

Шаг 1 из 11

Запрос и ответ

curl -I http://example.com
HTTP/1.1 200 OK
Date: Sat, 24 Oct 2026 16:52:33 GMT
Content-Type: text/html; charset=utf-8
Connection: keep-alive
Server: cloudflare
Allow: GET, HEAD
alt-svc: h3=":443"; ma=86400

HTTP, HyperText Transfer Protocol, работает по схеме «запрос и ответ». Клиент, например браузер или curl, открывает TCP-соединение с сервером, отправляет запрос и получает ответ. Сервер сам разговор не начинает. Обычный HTTP идёт на порт 80. Ключ -I просит у сервера только заголовки ответа, без самой страницы. Заголовки здесь это строки вида Имя: значение под первой строкой, служебные сведения об ответе: дата, тип содержимого, кто сервер. Подробно они в шагах 3 и 5.

200 OK в первой строке значит «всё хорошо, вот ресурс». Ресурс это то, что лежит по адресу: страница, картинка, файл, данные.

HTTP: клиент спрашивает, сервер отвечает, поверх TCP, порт 80.

URL по частям

https://urfu.ru:443/ru/students/?page=2
|___|   |_____||__||__________||_____|
схема   хост   порт  путь       параметры

URL это адрес ресурса. Схема говорит, каким протоколом идти: http или https. Хост это имя сервера. Порт можно не писать, тогда берётся порт схемы по умолчанию: 80 для http, 443 для https. Путь указывает ресурс на сервере. После знака ? идут параметры вида имя=значение, между собой через &.

Имя хоста браузер сначала переводит в IP-адрес через DNS, это последний урок предмета. Потом открывает TCP-соединение на IP и порт.

Шаг 3 из 11

Из чего состоит запрос

curl -v http://example.com/ -o nul
> GET / HTTP/1.1
> Host: example.com
> User-Agent: curl/8.21.0
> Accept: */*
>

Запрос HTTP/1.1 это обычный текст из четырёх частей. Стартовая строка: метод, путь, версия. Метод говорит, что сделать, GET значит «дай», остальные методы в шаге 4. Заголовки: по одному на строку, в виде Имя: значение. Пустая строка: «заголовки кончились». Тело: данные, которые клиент отправляет, у GET его нет.

В новой версии HTTP/2 те же части едут не текстом, а в двоичной записи, но смысл полей тот же. Заголовок Host обязателен: на одном IP живёт много сайтов, и сервер по нему понимает, какой нужен.

Ключ -v показывает весь разговор, строки со знаком > ушли от тебя. -o nul выбрасывает тело страницы, чтобы оно не мешало. User-Agent сообщает, кто спрашивает, Accept какие ответы клиент примет, */* значит любые.

GET /news?id=5 HTTP/1.1
Host: example.com

Параметры остаются в пути, хост уходит в заголовок, в конце пустая строка.

Писать в стартовой строке весь URL со схемой и хостом, GET http://example.com/news. Обычному серверу шлют только путь, а хост отдельно в Host.

Запрос: стартовая строка, заголовки, пустая строка, тело.

Код состояния это трёхзначное число в строке статуса, по первой цифре понятно, что случилось.

первая цифразначитчастые коды
1xxинформация
2xxуспех200 OK, 201 создано
3xxперенаправление301 переехал навсегда, новый адрес в заголовке Location, 304 не изменился, бери из кэша
4xxошибка клиента400 кривой запрос, 401 нужно войти, 403 запрещено, 404 не найдено

Кэш это копия, которую браузер сохранил в прошлый раз. 500 бывает, например, когда в коде сервера вылетело исключение. 502 значит, что промежуточный сервер получил кривой ответ от следующего. 503 значит, что сервер перегружен или на обслуживании. Коды описаны в RFC 9110.

GitHub по http сразу отправляет на https, отсюда 301. Поста 999 на учебном сервере нет, отсюда 404. Ключ -s убирает полосу загрузки, -o nul выбрасывает тело, а -w "%{http_code}" печатает только код.

Шаг 7 из 11

Безопасные и идемпотентные методы

Пользователь дважды нажал «Оформить заказ», и запрос POST ушёл два раза. В базе два заказа.

Безопасный метод ничего не меняет на сервере: GET и HEAD. Идемпотентный метод при повторе даёт тот же результат, что один раз: GET, HEAD, PUT, DELETE. POST не идемпотентный: каждый вызов создаёт новый ресурс. PUT говорит «положи вот это по такому адресу», и повтор кладёт то же самое на то же место.

DELETE идемпотентный, хотя второй вызов может вернуть 404: ресурса уже нет. Важен не код ответа, а состояние сервера после запроса, оно одно и то же.

Как всё же повторять POST без двойного заказа. Клиент придумывает для заказа уникальный номер и шлёт его в заголовке, часто его зовут Idempotency-Key. Сервер запоминает номера. Пришёл тот же номер второй раз, новый заказ он не создаёт и возвращает прошлый ответ.

Сделай сам. Связь оборвалась, и программа не знает, дошёл ли запрос. Какие запросы можно смело отправить ещё раз: GET новостей, POST платежа, PUT профиля, DELETE файла?
Показать ответСкрыть ответ

GET, PUT и DELETE можно повторить, результат не изменится. POST платежа повторять опасно: может списать деньги дважды.

Считать, что безопасный и идемпотентный одно и то же. PUT и DELETE меняют сервер, значит не безопасные, но повтор ничего не добавляет, значит идемпотентные.

Безопасные: GET, HEAD. Идемпотентные: GET, HEAD, PUT, DELETE.

POST повторять опасно.

Шаг 8 из 11

Без состояния и cookie

curl -I https://github.com/
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Set-Cookie: logged_in=no; expires=Sun, 24 Oct 2027 16:58:52 GMT; domain=.github.com; path=/; HttpOnly; secure; SameSite=Lax

HTTP без состояния, по-английски stateless: сервер обрабатывает каждый запрос как первый и не помнит прошлые. Чтобы сайт «помнил» вход или корзину, есть cookie. Сервер отдаёт заголовок Set-Cookie: имя=значение, браузер запоминает и в каждом следующем запросе к этому сайту шлёт Cookie: имя=значение.

У GitHub в ответе три Set-Cookie, здесь один. logged_in=no значит «не вошёл». После входа сервер выдаёт cookie с номером сессии, то есть твоего входа от логина до выхода, и по нему узнаёт тебя в каждом запросе. Слова после logged_in=no это настройки cookie: до какой даты хранить, для какого сайта, слать только по HTTPS.

Шаг 9 из 11

Одно соединение на много запросов

В ответах выше были строки Connection: keep-alive и alt-svc: h3=":443".

В HTTP/1.0 на каждый файл открывалось новое TCP-соединение: страница с 20 картинками стоила 20 рукопожатий. В HTTP/1.1 соединение постоянное, keep-alive: после ответа его не закрывают, и следующие запросы идут по нему же. HTTP/2 гонит много запросов по одному соединению одновременно. HTTP/3 работает поверх UDP и протокола QUIC, по плану курса это отдельная тема.

alt-svc: h3=":443" сервер сообщает: «я умею HTTP/3 на порту 443». Браузер в следующий раз может пойти туда.

Сделай сам. Страница из HTML, стиля и 8 картинок. Сколько TCP-рукопожатий нужно в HTTP/1.0 и сколько в HTTP/1.1 с keep-alive, если браузер держит одно соединение?
Показать ответСкрыть ответ

Файлов 1 + 1 + 8 = 10. В HTTP/1.0 десять рукопожатий. С keep-alive одно, все десять запросов идут по нему подряд.

Думать, что HTTP/3 «просто новее HTTP/1.1» и работает так же поверх TCP. Он ушёл на UDP, чтобы не ждать рукопожатие TCP и не тормозить все запросы из-за одного потерянного пакета.

HTTP/1.1: keep-alive, одно соединение на много запросов.

Шаг 10 из 11

HTTPS: тот же HTTP в шифре

http://example.com    TCP, порт 80,  текст виден по дороге
https://example.com   TCP, порт 443, сначала TLS, внутри тот же HTTP

HTTPS это HTTP внутри зашифрованного соединения TLS, порт 443. Сначала клиент и сервер по TLS договариваются о ключах, секретных числах, которыми шифруют данные. Ещё клиент проверяет сертификат сайта. Это электронный документ, заверенный доверенной организацией, по нему видно, что сервер правда github.com, а не подделка. Потом идут обычные запросы и ответы, только зашифрованные. Сообщения те же, что в шагах 3 и 5.

По HTTP пароль, cookie и ключ летят открытым текстом, их видит любой в той же Wi-Fi сети. Поэтому почти все сайты переводят на HTTPS, как GitHub кодом 301 в шаге 6.

IP-адрес сервера и порт 443 видны, они в заголовках IP и TCP снаружи шифра. Обычно видно и имя сайта, его клиент называет в начале TLS. Путь, заголовки, cookie и текст ответа зашифрованы.

Шаг 11 из 11

Postman и Wireshark на лабе

По слайдам лекции 1 на лабах два инструмента. Оба бесплатные, ставятся с официальных сайтов.

Postman:    New → HTTP → метод GET → URL → Send
            внизу: Status 200 OK, вкладки Body и Headers
Wireshark:  интерфейс Wi-Fi → синий плавник (старт)
            фильтр: http   → видны строки GET и HTTP/1.1 200
            фильтр: tls    → видно соединение на 443, текста нет

Postman это программа, которая отправляет HTTP-запросы с окнами вместо командной строки: выбрал метод, вписал URL, во вкладках Headers и Body добавил заголовки и тело, нажал Send. Wireshark перехватывает все пакеты на сетевом адаптере и раскладывает каждый по уровням: Ethernet или Wi-Fi, IP, TCP, HTTP. Это та самая инкапсуляция из урока про основы.

Чтобы увидеть HTTP открытым текстом, в Wireshark открой http://example.com, без S. По https фильтр http ничего не покажет: содержимое зашифровано.
