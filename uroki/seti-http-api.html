JSON: как выглядят данные

{
  "id": 1,
  "name": "Leanne Graham",
  "email": "Sincere@april.biz",
  "active": true,
  "phone": null,
  "address": { "city": "Gwenborough", "zipcode": "92998-3874" },

JSON это текстовый формат данных. Объект в фигурных скобках состоит из пар "ключ": значение через запятую. Ключ всегда в двойных кавычках. Значение бывает строкой в двойных кавычках, числом, true или false, null «ничего», другим объектом или списком в квадратных скобках.

Пример это пользователь 1 с учебного сервера jsonplaceholder, часть полей и два последних добавлены для наглядности. Вложенный объект address читается как «у пользователя есть адрес, а у адреса город».

Писать JSON как словарь Python или объект JavaScript. Там можно одинарные кавычки и лишнюю запятую, а JSON их не прощает, и сервер ответит 400.

JSON: {"ключ": значение}, ключи и строки в двойных кавычках.

Шаг 3 из 11

REST: у каждого ресурса свой адрес

/posts            все посты
/posts/1          пост номер 1
/posts/1/comments комментарии к посту 1
/users/1          пользователь 1
/users/1/posts    посты пользователя 1

REST это стиль устройства API. В нём всё, с чем работает API, называют ресурсами: пост, пользователь, заказ. У каждого ресурса свой адрес из существительных: /posts/1, а не /getPost?id=1. Что сделать с ресурсом, говорит метод HTTP, а не адрес. Сервер не хранит состояние клиента между запросами, как сам HTTP.

Набор однотипных ресурсов называют коллекцией и пишут во множественном числе: /posts. Один элемент коллекции это /posts/1.

Шаг 4 из 11

Методы на ресурсах

GET     /posts      список               200
GET     /posts/1    один пост            200 или 404
POST    /posts      создать новый        201
PUT     /posts/1    заменить целиком     200
PATCH   /posts/1    поменять часть полей 200
DELETE  /posts/1    удалить              200 или 204

Четыре действия с данными, создать, прочитать, изменить, удалить, по-английски называют CRUD. В REST они ложатся на методы: создать POST в коллекцию, прочитать GET, изменить PUT или PATCH, удалить DELETE. PATCH отличается от PUT тем, что присылают только меняемые поля, а не весь ресурс. 204 значит «готово, тела в ответе нет».

Шаг 8 из 11

API-ключ и ответ 401

curl -i https://api.github.com/user
HTTP/1.1 401 Unauthorized
Content-Type: application/json; charset=utf-8
X-RateLimit-Limit: 60
X-RateLimit-Remaining: 56

{
  "message": "Requires authentication",
  "documentation_url": "https://docs.github.com/rest",
  "status": "401"
}

API-ключ, или токен, это длинная секретная строка, по которой API узнаёт, кто к нему пришёл и что ему можно. Его выдают в личном кабинете сервиса. Чаще всего ключ передают в заголовке: Authorization: Bearer ключ. Слово Bearer по-английски значит «предъявитель», оно говорит серверу, что дальше идёт токен. Без ключа закрытый адрес отвечает 401 Unauthorized: «представься». С ключом, но без прав, ответ 403.

curl https://api.github.com/user -H "Authorization: Bearer ghp_твой_токен"

Адрес /user значит «я сам», серверу нужен ключ, чтобы понять, кто это «я». Публичный /users/octocat из шага 1 работал без ключа. Заголовки X-RateLimit в ответе разберёт шаг 11.

Сделай сам. Запрос с ключом вернул 403, а без ключа 401. Что не так в каждом случае?
Показать ответСкрыть ответ

401: сервер не знает, кто ты, ключа нет или он неверный. 403: ключ верный, но у него нет прав на этот ресурс, например токен выпущен только на чтение.

Писать в заголовке Authorization: ghp_… без слова Bearer или наоборот Bearer: ghp_… с двоеточием. Формат строгий: имя заголовка, двоеточие, Bearer, пробел, ключ.

Ключ в заголовке: Authorization: Bearer ключ.

Нет ключа 401, нет прав 403.

Шаг 9 из 11

Почему ключ нельзя светить

У Телеграма ключ бота входит прямо в путь адреса. Запрос с выдуманным ключом:

curl -i https://api.telegram.org/bot123:fake/getMe
HTTP/1.1 401 Unauthorized
Content-Type: application/json

{"ok":false,"error_code":401,"description":"Unauthorized"}

Ключ работает как пароль: любой, у кого он есть, действует от твоего имени. Отправляет сообщения от бота, тратит деньги на платном API, читает данные. Ключи утекают через код на GitHub, скриншоты, сообщения в чатах, историю команд и журналы серверов, куда пишется полный URL. Утёк ключ, его сразу отзывают в кабинете сервиса и выпускают новый: удалить из кода мало, копии уже остались.

Публичные репозитории GitHub постоянно сканируют чужие программы в поисках ключей, и токен, выложенный в коммите, находят за минуты. У Телеграма новый токен выдаёт @BotFather командой /revoke.

Показать ответСкрыть ответ

Нет. Старый коммит с токеном остаётся в истории репозитория, и его могли скопировать за эту минуту. Токен нужно отозвать и выпустить новый.

Прятать ключ, разрезав его на куски в коде или закодировав. Любой, кто читает код, соберёт его обратно. Ключ не должен попадать в код вообще, это следующий шаг.

Не в код, не в скриншот, не в чат.

Шаг 11 из 11

Лимиты запросов и код 429

В ответе шага 8 были заголовки X-RateLimit-Limit: 60 и X-RateLimit-Remaining: 56.

Лимит запросов, rate limit, это сколько запросов API разрешает за отрезок времени. GitHub без ключа даёт 60 запросов в час с одного адреса, Remaining показывает, сколько осталось. Превысил лимит, сервер отвечает 429 Too Many Requests, часто с заголовком Retry-After: через сколько секунд можно снова. С ключом лимит обычно больше, ещё одна причина передавать ключ.

Правильная реакция программы на 429: подождать и повторить, каждый раз ожидая дольше. Повторять сразу в цикле бесполезно, это только продлевает блокировку.

Сделай сам. Бот делает 2 запроса к API каждую минуту. Хватит ли ему лимита 60 запросов в час без ключа?
Показать ответСкрыть ответ

Нет. 2 × 60 = 120 запросов в час, вдвое больше лимита. Через 30 минут пойдут ответы 429. Нужен ключ с большим лимитом или реже спрашивать.

Путать 429 с 503. 429 значит «ты слишком часто спрашиваешь», виноват клиент. 503 значит «сервер перегружен вообще», виновата сторона сервера.

Лимит: X-RateLimit-Remaining, превысил 429.

На 429 ждать и повторять реже.
