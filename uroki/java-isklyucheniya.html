Исключения и null

Java · лекция 5, 12.10 (Корелин), слайды seminar_4 и код seminar2: UserService, Optional · на зачёт · около 65 минут

Исключения ты уже видел: деление на ноль, выход за массив, IllegalArgumentException из урока инкапсуляция. Там программа просто падала. Здесь научимся ловить ошибку и продолжать работу, отличать два вида исключений, писать своё, закрывать файлы автоматически и жить с null без падений.

Примеры по слайдам лекции и по коду seminar2, где Корелин показывал своё исключение и Optional. Нужны уроки про наследование и лямбды.

try и catch: поймать и продолжить

String[] inputs = {"42", "abc", "7"};
int sum = 0;
for (String s : inputs) {
    try {
        int x = Integer.parseInt(s);
        sum += x;
        System.out.println("Прибавил " + x);
    } catch (NumberFormatException e) {
        System.out.println("Не число: " + e.getMessage());
    }
}

try, «попробуй», обводит код, где может случиться ошибка. catch, «поймай», говорит, какое исключение ловить и что тогда делать. Как только в try вылетело исключение, остаток блока пропускается, и управление переходит в catch. Объект исключения лежит в переменной e, e.getMessage() отдаёт его текст. После catch программа идёт дальше: цикл обработал «7», сумма 42 + 7 = 49.

Шаг 5 из 11

Проверяемые и непроверяемые

import java.io.FileReader;

public class Main {
    public static void main(String[] args) {
        FileReader reader = new FileReader("marks.txt");
        System.out.println("Открыл");
    }
}
Main.java:5: error: unreported exception FileNotFoundException; must be caught or declared to be thrown
        FileReader reader = new FileReader("marks.txt");
                            ^
1 error

Слайды делят исключения на два вида. Проверяемые, checked, компилятор проверяет при сборке: если метод может их бросить, ты обязан поймать или объявить. Это все наследники Exception, кроме ветки RuntimeException. Типичные: нет файла, оборвалась сеть. Это беды снаружи, программа в них не виновата, но готова к ним быть обязана. Непроверяемые, unchecked, это RuntimeException и наследники: деление на ноль, выход за массив, NullPointerException. Компилятор про них молчит, это ошибки в самом коде, их обычно исправляют, а не ловят. Исключение из правила: разбор чужого ввода, как parseInt в шаге 2, заранее не проверишь, его ловят.

Ошибка выше: «необъявленное исключение FileNotFoundException, его надо поймать или объявить». С try всё собирается:

try {
    FileReader reader = new FileReader("marks.txt");
    System.out.println("Открыл");
} catch (FileNotFoundException e) {
    System.out.println("Нет файла: " + e.getMessage());
}
Нет файла: marks.txt (Не удается найти указанный файл)

Текст в скобках пишет Windows, на другой системе он свой. Для FileNotFoundException нужен import java.io.FileNotFoundException;.

Показать ответСкрыть ответ

Проверяемое FileNotFoundException. Посмотреть родителей: в IDEA Ctrl+H по имени класса показывает иерархию. NumberFormatException потомок RuntimeException, значит непроверяемое, поэтому parseInt в шаге 1 собирался без try.

Считать, что «проверяемое» значит «серьёзнее». Деление на ноль уронит программу так же. Разница только в том, следит ли компилятор.

Checked, наследники Exception: компилятор заставит поймать или объявить.

Unchecked, наследники RuntimeException: ошибки кода, компилятор молчит.

Второй способ выполнить требование компилятора: throws в заголовке метода, «этот метод может бросить такое исключение». Метод сам его не ловит, а передаёт тому, кто его вызвал. Исключение летит вверх по цепочке вызовов, пока кто-то не поймает. Здесь не поймал никто, даже main, и в трассе видна вся цепочка снизу вверх: main вызвал load, тот open.

Шаг 7 из 11

throw и своё исключение

По мотивам UserService из seminar2: пользователя ищут по номеру, не нашли, бросают своё исключение.

class UserNotFoundException extends Exception {
    public UserNotFoundException(int id) {
        super("Пользователь " + id + " не найден");
    }
}

class UserService {
    private final Map<Integer, String> users = new HashMap<>();

    public UserService() {
        users.put(1, "Alice");
        users.put(2, "Bob");
    }

    public String getUserOrException(int id) throws UserNotFoundException {
        String user = users.get(id);
        if (user == null) {
            throw new UserNotFoundException(id);
        }
        return user;
    }
}
UserService service = new UserService();
int[] ids = {2, 7};
for (int id : ids) {
    try {
        System.out.println("Нашёл " + service.getUserOrException(id));
    } catch (UserNotFoundException e) {
        System.out.println(e.getMessage());
    }
}
Нашёл Bob
Пользователь 7 не найден

Своё исключение это обычный класс-наследник. Унаследовал Exception, значит проверяемое, RuntimeException, значит непроверяемое. Текст передают родителю через super(…), и его потом отдаёт getMessage(). throw new … бросает объект, ты делал это с IllegalArgumentException. Map здесь словарь «номер → имя». put(1, "Alice") кладёт пару «номер и имя», get(номер) достаёт имя или возвращает null, если номера нет. Нужны import java.util.HashMap; и import java.util.Map;.

Имя исключения говорит, что случилось, лучше любого текста: UserNotFoundException ловят отдельно от остальных ошибок.

Шаг 8 из 11

try-with-resources: закрыть само

class Connection implements AutoCloseable {
    private final String name;

    public Connection(String name) {
        this.name = name;
        System.out.println("открыл " + name);
    }

    public void send(String text) {
        if (text.isEmpty()) {
            throw new IllegalArgumentException("пустое сообщение");
        }
        System.out.println(name + " отправил: " + text);
    }

    @Override
    public void close() {
        System.out.println("закрыл " + name);
    }
}
try (Connection c = new Connection("база")) {
    c.send("привет");
    c.send("");
    c.send("сюда не дойдём");
} catch (IllegalArgumentException e) {
    System.out.println("ошибка: " + e.getMessage());
}
System.out.println("дальше");
открыл база
база отправил: привет
закрыл база
ошибка: пустое сообщение
дальше

Ресурс это то, что надо вернуть после работы: открытый файл, соединение с базой или сетью. Слайд: try-with-resources, с Java 7, сам закрывает ресурсы с интерфейсом AutoCloseable. Ресурс создают в круглых скобках после try. Когда блок кончился, нормально или исключением, Java вызывает close(). По выводу видно: «закрыл» напечатано раньше, чем сработал catch. Это та же уборка, что в finally, только её нельзя забыть.

Файлы, Scanner и соединения Java уже реализуют AutoCloseable: try (Scanner in = new Scanner(new File("marks.txt"))) { … }.

В обратном порядке: последний открытый закрывается первым. B может зависеть от A, например запрос от соединения, и закрывать A раньше нельзя.

Положить в скобки try объект, который не реализует AutoCloseable. Компилятор ответит try-with-resources not applicable to variable type: закрывать нечем.

try (Ресурс r = new Ресурс()) { … }: close() вызовется сам.

Ресурс должен реализовать AutoCloseable, закрываются в обратном порядке.

null значит «значения нет», ты встречал его в уроке про классы. Слайд: Тони Хоар, придумавший null в 1965, назвал его своей ошибкой на миллиард долларов. Optional<T> это коробка, в которой значение есть или его нет. Метод, который может не найти, возвращает коробку, и сам тип говорит: «проверь».
