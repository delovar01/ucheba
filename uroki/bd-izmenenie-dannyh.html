Добавить, поправить, удалить: INSERT, UPDATE, DELETE

Базы данных · лекция 4 от 13.10, домашка 4 · около 50 минут

До сих пор ты только читал базу через SELECT. Здесь три команды, которые её меняют: INSERT добавляет строки, UPDATE правит, DELETE удаляет. Всё на твоей базе ml_tracker, а после каждой правки проверяем результат через SELECT … WHERE. Ровно это и просят в домашке 4.

Как проходить: читаешь шаг, решаешь «сделай сам» сам и только потом открываешь ответ. Рамку «Главное из шага» перепиши в тетрадь. Если в шаге что-то непонятно, дальше не иди: сначала задай вопрос по этому шагу.

Важно: эти команды меняют базу по-настоящему. На этой же базе ты делаешь самостоятельную 2, и чужие строки испортят её ответы. Поэтому в уроке каждая правка идёт внутри пробы, которая потом всё отменяет. Как она устроена, в шаге 1.

Шаг 1 из 10

Проба: BEGIN и ROLLBACK

Сначала учимся отменять, а потом уже менять. Вот проба целиком. Средняя строка добавляет исследователя, как она устроена, разберём в шаге 2. Сейчас смотри только на первую и последнюю.

BEGIN;
INSERT INTO researchers (full_name, email, grp)
VALUES ('Козлов Илья', 'ilya@urfu.ru', 'РИ-250932');
SELECT COUNT(*) FROM researchers;   -- 5
ROLLBACK;
SELECT COUNT(*) FROM researchers;   -- 4

Транзакция это пачка команд, которая сохраняется вся целиком или не сохраняется вообще. BEGIN открывает пачку. ROLLBACK отменяет всё, что было после BEGIN. COMMIT вместо него сохранил бы.

Внутри пробы база ведёт себя по-настоящему: первый COUNT видит Козлова, исследователей 5. После ROLLBACK его как не бывало, снова 4.

Без BEGIN каждая команда сохраняется сразу, как только выполнилась. Отменить её потом нечем.

В DBeaver выделяй и запускай всю пробу разом, от BEGIN до ROLLBACK, сочетанием Alt+X (выполнить скрипт). Тогда результат каждого SELECT откроется своей вкладкой внизу.

Сделай сам. Внутри одной пробы запустили INSERT Козлова, потом SELECT COUNT(*), потом ROLLBACK, потом ещё раз SELECT COUNT(*). А потом то же самое без строки BEGIN. Что покажет последний COUNT в каждом случае?
Показать ответСкрыть ответ

С BEGIN будет 4: вставка отменилась. Без BEGIN будет 5, Козлов остался в базе навсегда. ROLLBACK без открытой пробы ничего не отменяет, база только предупредит: there is no transaction in progress, «пробы нет».

Думать, что ROLLBACK это «отмена последней команды», как Ctrl+Z. Он отменяет только то, что было после BEGIN. Нет BEGIN, нечего отменять. Если Козлов всё же попал в базу, удали его командой из шага 8 или верни базу целиком (как, в конце урока).

BEGIN; … ROLLBACK; проба, всё отменится. BEGIN; … COMMIT; сохранить.

Без BEGIN команда сохраняется сразу.

Шаг 2 из 10

INSERT: добавить одну строку

Это первая часть домашки. Добавляем нового исследователя и сразу проверяем, что он появился.

BEGIN;
INSERT INTO researchers (full_name, email, grp)
VALUES ('Козлов Илья', 'ilya@urfu.ru', 'РИ-250932');

SELECT id, full_name, email, grp, created_at
FROM researchers
WHERE email = 'ilya@urfu.ru';
ROLLBACK;

INSERT INTO таблица (столбцы) VALUES (значения) добавляет строку. В первых скобках столбцы, во вторых значения в том же порядке: первое значение уйдёт в первый столбец, второе во второй.

id мы не писали. У него тип SERIAL, это счётчик: база сама даёт следующий номер. Последний был 4, Козлов получит 5. created_at тоже не писали, у него правило DEFAULT now(): «если не сказали, ставь текущее время».

idfull_nameemailgrpcreated_at
5Козлов Ильяilya@urfu.ruРИ-250932время, когда запустил

Проверка ищет его по почте, а не по имени: почта уникальная, найдётся ровно одна строка. В DBeaver после INSERT внизу будет «Updated Rows: 1», то есть добавлена одна строка.

Номер может оказаться не 5, а 6 или 7. Счётчик SERIAL пробой не откатывается: каждый запуск пробы забирает номер насовсем. Это нормально, номера просто пропускаются.

Сделай сам. Внутри пробы добавь модель XGBoost, фреймворк xgboost, параметров 0.3, и проверь через SELECT … WHERE. Какой номер она получит на свежей базе?

Номер 6 (моделей было 5), countpar покажется как 0.30: у столбца два знака после точки. Текст в одинарных кавычках, число без кавычек.

Вписать id руками: INSERT INTO researchers (id, full_name, …) VALUES (1, …). Номер 1 уже занят Степаном, и база ответит duplicate key value violates unique constraint "researchers_pkey", «такой ключ уже есть». id с SERIAL не пиши, его выдаёт база.

INSERT INTO t (a, b) VALUES ('x', 1); столбцы и значения по порядку.

id и столбцы с DEFAULT можно не писать. Проверка: SELECT … WHERE по уникальному столбцу.

Шаг 4 из 10

INSERT со ссылками: база проверяет номера

Запуск хранит номера исследователя, набора и модели. Степан (1) учит RandomForest (2) на MNIST (5), 7 эпох.

BEGIN;
INSERT INTO experiments (researcher_id, dataset_id, model_id, count_apoh)
VALUES (1, 5, 2, 7);

SELECT id, researcher_id, dataset_id, model_id, count_apoh, status
FROM experiments
WHERE id = 10;
ROLLBACK;

Получится строка 10 со статусом running: у status стоит DEFAULT 'running', а created_at возьмёт текущее время.

Столбец researcher_id объявлен как внешний ключ (REFERENCES researchers(id)): в нём может стоять только номер, который есть в researchers. Попробуй исследователя 99:

INSERT INTO experiments (researcher_id, dataset_id, model_id, count_apoh)
VALUES (99, 5, 2, 7);

База откажет: violates foreign key constraint "experiments_researcher_id_fkey", «нарушен внешний ключ». Исследователя 99 нет, ссылаться не на кого.

Если ошибка случилась внутри пробы, база дальше ничего не выполняет и на каждую команду отвечает current transaction is aborted, «проба сломана». Выход один: ROLLBACK и начать пробу заново.

Сделай сам. Что ответит база на запуск с нулём эпох: VALUES (1, 5, 2, 0)? Почему?

Откажет: violates check constraint "experiments_count_apoh_check". У count_apoh правило CHECK (count_apoh BETWEEN 1 AND 1000), а 0 меньше 1. Строка не добавится.

Читать ошибку как «база сломалась». Наоборот, это база тебя защитила: правила CHECK и внешних ключей ты сам поставил в самостоятельной 1. В названии в кавычках сказано, какое правило сработало: count_apoh_check, значит дело в числе эпох.

Внешний ключ: номер должен существовать в справочнике, иначе ошибка.

Шаг 5 из 10

UPDATE: поправить один столбец

Это вторая часть домашки. Запуск 8 досчитался, ставим ему статус done.

BEGIN;
UPDATE experiments
SET status = 'done'
WHERE id = 8;

SELECT id, status FROM experiments WHERE id = 8;
ROLLBACK;

UPDATE таблица SET столбец = новое значение WHERE условие меняет значение в строках, для которых условие верно. SET значит «поставить». WHERE работает так же, как в SELECT: выбирает строки.

Внизу DBeaver покажет «Updated Rows: 1», а проверка выведет 8 | done. Проверка повторяет то же WHERE, что было в UPDATE: так видно именно ту строку, которую трогали.

Сделай сам. У Titanic нет ссылки. Поставь ей https:\\titanic и проверь.

BEGIN;
UPDATE datasets
SET link = 'https:\\titanic'
WHERE name = 'Titanic';

SELECT name, link FROM datasets WHERE name = 'Titanic';
ROLLBACK;

Updated Rows: 1, в проверке Titanic | https:\\titanic. Можно и WHERE link IS NULL: пустая ссылка только у Titanic.

Написать WHERE link = NULL. Ошибки не будет, но «Updated Rows: 0», не поменялось ничего. Пустоту ищут только через IS NULL, как в шаге 8 урока про фильтры. Всегда смотри на число изменённых строк: 0 значит, что WHERE ничего не нашёл.

UPDATE t SET столбец = значение WHERE условие;

Шаг 6 из 10

UPDATE: несколько столбцов и расчёт от старого значения

Запуск 8 дообучили ещё на 5 эпох и закончили. Меняем два столбца сразу.

    status     = 'done'

В SET можно перечислить несколько столбцов через запятую. А справа от = может стоять расчёт со старым значением: count_apoh + 5 значит «возьми, сколько было, и прибавь 5».

Было 10 эпох, стало 15, статус done. Проверка: 8 | 15 | done.

Сделай сам. Всем запускам Ивановой Марии (её номер 3) прибавь одну эпоху. Сколько строк изменится и какие эпохи будут в проверке?

SET a = 1, b = 'x' через запятую, не через AND.

Шаг 7 из 10

Сначала SELECT, потом правка

Азат перевёлся в группу РИ-250931. Главная опасность UPDATE и DELETE в том, что без WHERE они меняют все строки таблицы, и база не переспросит.

UPDATE researchers SET grp = 'РИ-250931';   -- без WHERE: Updated Rows: 4

Все четыре исследователя, включая Олега без группы, окажутся в РИ-250931. Чтобы так не вышло, порядок всегда один.

Сначала пишешь SELECT с нужным WHERE и смотришь, какие строки попали. Потом меняешь начало запроса на UPDATE … SET или DELETE, а WHERE не трогаешь. Число в Updated Rows должно совпасть с числом строк в SELECT.

-- 1. смотрю, кого задену
SELECT id, full_name, grp
FROM researchers
WHERE full_name LIKE 'Щайхутдинов%';        -- одна строка, Азат

-- 2. то же WHERE, только начало другое
BEGIN;
UPDATE researchers
SET grp = 'РИ-250931'
WHERE full_name LIKE 'Щайхутдинов%';        -- Updated Rows: 1

SELECT id, full_name, grp
FROM researchers
WHERE full_name LIKE 'Щайхутдинов%';        -- 2 | Щайхутдинов Азат | РИ-250931
ROLLBACK;

Одна строка в SELECT, одна изменена. Сходится, значит задели того, кого хотели.

Сделай сам. Хотим удалить все оценки ниже 0.8. Напиши SELECT, который покажет, что удалится. Сколько строк и какие?
Показать ответСкрыть ответ 
SELECT id, experiments_id, name_metric, mean_metric
FROM metrics
WHERE mean_metric < 0.8;

Три строки: номер 1 (accuracy 0.787), номер 2 (f1 0.721), номер 4 (f1 0.789). Их и удалим в следующем шаге, с этим же WHERE.

Написать <= 0.8 или < 0.80 и думать, что разницы нет. Здесь ответ тот же, оценки ровно 0.8 нет. Но «ниже 0.8» это строго меньше, <. Если бы оценка 0.800 была, <= удалил бы лишнюю.

Порядок: SELECT … WHERE → посмотрел → то же WHERE в UPDATE/DELETE.

Без WHERE меняются все строки таблицы.

Удалим запуск 6. У него две оценки, номера 9 и 10.

Шаг 10 из 10

UPSERT: вставь, а если уже есть, обнови

Это было на лекции 13.10. Пришли данные: Азат, azat@urfu.ru, группа РИ-250931. Обычный INSERT упадёт с duplicate key value violates unique constraint "researchers_email_key": такая почта уже есть.

BEGIN;
INSERT INTO researchers (full_name, email, grp)
VALUES ('Щайхутдинов Азат', 'azat@urfu.ru', 'РИ-250931')
ON CONFLICT (email) DO UPDATE SET grp = EXCLUDED.grp;

SELECT id, full_name, grp FROM researchers WHERE email = 'azat@urfu.ru';
SELECT COUNT(*) FROM researchers;   -- 4, нового не добавилось
ROLLBACK;

ON CONFLICT (email) значит «если строка с такой почтой уже есть». DO UPDATE SET говорит, что тогда поправить. EXCLUDED это та строка, которую мы пытались вставить: EXCLUDED.grp равно РИ-250931.

Проверка: 2 | Щайхутдинов Азат | РИ-250931. Номер остался 2, строка та же, новой не появилось. В скобках после ON CONFLICT пишут столбец с UNIQUE или первичным ключом, иначе базе не с чем сравнивать.

Сделай сам. Что будет, если вместо DO UPDATE SET … написать DO NOTHING, а группу дать РИ-250999?

INSERT INTO researchers (full_name, email, grp)
VALUES ('Щайхутдинов Азат', 'azat@urfu.ru', 'РИ-250999')
ON CONFLICT (email) DO NOTHING;

Ошибки не будет, но и ничего не поменяется: Updated Rows: 0, у Азата старая группа. DO NOTHING значит «есть такой, молча пропусти». Удобно, когда заливаешь данные повторно и дубли не нужны.

Написать ON CONFLICT (full_name). Имя не помечено UNIQUE, и база ответит there is no unique or exclusion constraint matching the ON CONFLICT specification, «нет уникального правила под это». Конфликт бывает только по уникальному столбцу.

INSERT … ON CONFLICT (уникальный столбец) DO UPDATE SET a = EXCLUDED.a;

DO NOTHING пропустить дубль. EXCLUDED это вставляемая строка.

Как это ложится на домашку 4

  • INSERT: шаги 2–4. Добавь по строке в несколько своих таблиц и хотя бы раз несколько строк одним запросом.
  • UPDATE: шаги 5–6. Одна правка одного столбца и одна с расчётом от старого значения.
  • DELETE: шаги 8–9. Одно простое удаление и одно, где видно каскад.
  • Проверка: после каждой команды SELECT с тем же WHERE, порядок из шага 7.

Для сдачи над каждой командой пиши комментарий -- что делаю, под ней проверку, и делай скрин результата проверки. Строки придумай свои, а не из урока: другой исследователь, другой набор, другое число.

Сначала сдай самостоятельную 2. Домашку делай по-настоящему, без ROLLBACK (или с COMMIT), уже после неё: новые строки поменяют ответы самостоятельной.

Если база запуталась и хочется как было: в DBeaver по очереди запусти два файла базы, 1-baza-ml_tracker.sql и потом 2-dopolnenie-pod-sr2.sql. Первый удаляет все таблицы и создаёт заново, второй дописывает строки. После них база точно такая, как в начале урока.
